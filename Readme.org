** How does it look?

Below is some general usage. Remember, this is an immutable data structure that does path copying. This means an update or addition usually only incurs a small copy penalty. It is of course almost always slower than a mutable dictionary, but still pretty fast. I can confidently say that operation for operation this implementation is faster than doing the same thing with clojure's maps, and people are using those for serious business™.


#+begin_src csharp
using Map;

// --- 1. Basic Initialization & Persistence ---
var map1 = Map<string, int>.Empty.Add("Alice", 25).Add("Bob", 30);
var map2 = map1.Remove("Alice"); // Returns a new map without Alice

Console.WriteLine($"Map1 has Alice: {map1.ContainsKey("Alice")}"); // True
Console.WriteLine($"Map2 has Alice: {map2.ContainsKey("Alice")}"); // False

// --- 2. Retrieval & Properties ---
int bobAge = map1["Bob"]; // Throws KeyNotFoundException if missing
bool hasCharlie = map1.TryGetValue("Charlie", out int charlieAge);
Console.WriteLine($"Count: {map1.Count}, IsEmpty: {map1.IsEmpty}");

// --- 3. Enumeration ---
// Uses the struct-based MapEnumerator for zero-allocation iteration
foreach (var kvp in map1)
{
        Console.WriteLine($"{kvp.Key}: {kvp.Value}");
}

// --- 4. Raw Transient Interface ---
// Avoids allocating intermediate tree nodes for sequential updates
TransientMap<string, int> transientMap = map1.ToTransient();
transientMap.Add("Charlie", 35);
transientMap.Add("Dave", 40);
transientMap.Remove("Bob");

if (transientMap.TryGetValue("Charlie", out int val))
{
        // Retrieval works directly on the transient structure
}

// Commits changes and disowns the transient nodes
Map<string, int> map3 = transientMap.ToImmutable();

// --- 5. Bulk Construction via MapBuilder ---
// Uses highly optimized radix sort for fast initialization
var builder = new MapBuilder<string, int>(initialCapacity: 100);
for (int i = 0; i < 100; i++)
{
        builder.Add($"User{i}", i);
}
var map4 = builder.ToImmutable();

// --- 6. Functional Utilities & Searching ---
// MapCar: Transform keys and values into a new Map
var transformed = map1.MapCar((k, v) => (k.ToUpper(), v * 2));

// Filter: Retain elements matching a predicate
var filtered = transformed.Filter((k, v) => v > 50);

// FoldValues: Aggregate values sequentially
int sumOfAges = map1.FoldValues(0, (acc, v) => acc + v);

// Exists & FindKey
bool exists = map1.Exists((k, v) => v > 20);
string key = map1.FindKey(k => k.StartsWith("A"));

// Iter: Execute a delegate. Returning false aborts iteration early.
map1.Iter((k, v) => 
{
        if (k == "Bob") return false; // Abort early
            return true; 
});

// ForEach: Unconditional execution over all elements
map1.ForEach((k, v) => Console.WriteLine(k));

// --- 7. Merging Maps ---
// Resolves conflicts by explicitly preferring the right side's value
var map5 = map3.Merge(map1, conflictResolver: (k, left, right) => right);

#+end_src

** How fast?
 I would say fast. Not as much as I expected from my previous runs, but it is still very competitive. Here are some benchmarks for six different workloads. These are all <int, int> benchmarks, but things don't change much for strings when everyone uses the same kind of hashing algorithm. Using other keys just adds noise, since nobody uses a novel string key storage anyway. 

 The transient map is a map that allows for mutating updates on nodes that has no other owner. This allows for somewhat faster building, but very fast bulk updates. The builder is a specialized builder that adds all keys to a list, radix sorts them by the hash and builds the tree directly. It is very fast.

 Over all, when using all-persistent workloads (no transients or builders) it is around 2-10x faster than ImmDict (I didn't benchmark the ImmutableDict builder, though!), while being in the same ballpark with regards to memory usage.

** Who should use this?

Not a living soul. I remember feeling pretty confident it wasn't going to eat my face back in the day, but looking it it now it is doing a lot of unsafe memory access. For the love of god, just use LanguageExt.HashMap. It is fast and high quality.

This is a work in progress that will be the default hash map for my own little programming language. I will never work to make it open for general usage.

But please have a look at how I did things.

** Why is it fast?

The vast majority of nodes in a tree is going to be leaf nodes. In this code, I was inspired by the nightmare material that is scala's vectors. Not the memory layout or any of the code, but using different classes for every level of the tree. At first I tried using 32 different kinds of nodes that all packad Slot<K,V,Node>, but in the end that ended up wasting too much memory to be useful. At small and very large maps it was very fast, but at N=1000 ... 10000 it was slowish.  I then repurposed the nodes to be leaf nodes that packed Slot<K,V>, and letting the internal nodes be regular internal nodes with the bitmaps and the two customary array types of a champ (data, and node).

I also packed a ulong that contained the node capacity (used only in leaf nodes), node flags (that are set at creation, meaning I can safely Unsafe.As based on the node flags) and a 48 bit owner id (that is used by transient maps).

Why did I pack this in one ulong? Possibly because I didn't really trust the different Packing directives in dotnet. I had issues with reading protected memory, despite me being very diligent with how things were laid out. I might have been trying to avoid load instructions. 

Anyway, there are 32 different kinds of exact-fit leaf nodes. They contain a ulong meta and N inline slots. This removes one memory indirection compared to using regular arrays. I could probably have made 32 different kinds of inline nodes as well, but since I don't really know what I am going to use this for, i feel like it is a dumb bet. I am not even sure where the sweet spot is for class tree combinatorics. Perhaps am I already past it.

** What can be made faster?

I do think I am past the point where there are simple things that yield a large speedup, but there are still many things that can be done with regards to making it faster. With regards to leaf nodes, I am pretty sure they are pretty optimal except for the indirection when allocating.

Since most key-value-pairs are in the leaf nodes, we can do the same kind of 32-node thing for internalnodes. We allocate different internal nodes depending on child count, while keeping the data array as a regular array. This would even make them slightly more efficient since we shrink the overhead by 32 bytes (8 bytes less for the array pointer and 24 bytes less for the array header.)

What I really would like to do is to find a way to do dynamic inline arrays, where I can allocate a Node and tell the GC that there are N*NodePointers at the end. Right now I haven't figured that out.

I think some of the methods could be rewritten to be iterative rather than recursive. This was a slight win for TryGetValue, but that method is also the most sensitive.
